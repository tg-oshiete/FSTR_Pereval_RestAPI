# Контракт Pereval API

Текущая версия API работает с частными заявками автора и решениями модератора.
Базовый адрес локального запуска: `http://localhost:8000`. JSON передаётся в UTF-8
с `Content-Type: application/json`. Интерактивные схемы: `/docs`, `/redoc`,
`/openapi.json`; эти маршруты и `/health` не требуют авторизации.

## Авторизация и маршруты

Для прикладных запросов обязателен `Authorization: Bearer <token>`. Токен выдаётся
операторской CLI и связан с пользователем и ролью `author` или `moderator`.
Клиент не выбирает владельца заявки по ID и не назначает себе роль. Порядок
выдачи и отзыва: [ручной доступ](DEMO.md#ручной-доступ-в-swagger).

| Метод и путь | Успех | Правило доступа |
| --- | --- | --- |
| `POST /submitData/` | 201: `status`, `message`, `id` | Автор; профиль соответствует личности токена |
| `GET /submitData/{id}` | 200: полная заявка с фото | Владелец или модератор |
| `PATCH /submitData/{id}` | 200: `state: 1`, `message` | Владелец, только статус new |
| `GET /submitData/?user__email=...` | 200: массив кратких заявок | Автор — только свой email, модератор — любой |
| `GET /moderation/perevals?status=new` | 200: массив кратких заявок | Модератор |
| `PATCH /moderation/perevals/{id}/status` | 200: `id`, `status` | Модератор |
| `GET /submitData/{id}/history` | 200: массив решений | Владелец или модератор |

Модератор не создаёт заявки и не меняет их содержимое. Чужая заявка/история/email
недоступны автору. Все ID — положительные десятичные целые, 1–2147483647.
Списки принимают `limit` (1–100, по умолчанию 20) и `offset` (0–2147483647,
по умолчанию 0), отсортированы по `id ASC`. Отсутствие результатов — `[]`.
Статус очереди: new/pending/accepted/rejected, по умолчанию new.

## Создание и поля

Успешный POST возвращает:

```json
{"status":201,"message":"Отправлено успешно","id":42}
```

В этом ответе `status` — число HTTP-статуса; в GET это строка статуса модерации.
Новая заявка всегда `new`. Сервер назначает `id`, `date_added` и владельца.

| Поле POST | Обязательность | Допустимое значение |
| --- | --- | --- |
| `title` | Обязательно | Строка 1–255 |
| `beauty_title` | Можно опустить | Строка 1–255 или null |
| `other_titles` | Можно опустить | Строка 1–1024 или null |
| `connect` | Можно опустить | Строка 1–2000 или null |
| `add_time` | Можно опустить → текущее UTC | RFC 3339 с часовым поясом |
| `user` | Объект обязателен | email, fam, name; необязательные phone/otc |
| `user.email` | Обязательно | Валидный email, до 254 символов |
| `user.fam`, `user.name` | Обязательно | Строки 1–100 |
| `user.otc` | Можно опустить | Строка 1–100 или null |
| `user.phone` | Можно опустить | Строка 1–32 или null; это контакт, не проверенный номер |
| `coords.latitude` | Обязательно | Конечное JSON-число от −90 до 90 |
| `coords.longitude` | Обязательно | Конечное JSON-число от −180 до 180 |
| `coords.height` | Обязательно | Целое JSON-число 1–10000 |
| `level` | Объект обязателен; допустим `{}` | spring/summer/autumn/winter, каждый можно опустить или задать null |
| `images` | Можно опустить → `[]` | Массив объектов с title и img |
| `images[].title` | Обязательно для фото | Строка 1–255 |
| `images[].img` | Обязательно для фото | Строгий base64 JPEG/PNG |

Пропущенные необязательные строки/сезоны сохраняются как null. Строки обрезаются
по краям, длины считаются после этого; пустые/пробельные строки дают 422.
Управляющие символы запрещены; LF/TAB разрешены в `connect` и причине решения.
Неизвестные поля запрещены на каждом уровне, включая `status`, `role`, `user_id`
и `user.id`. Числа в строках и boolean вместо чисел не принимаются; дробная
высота, NaN и Infinity запрещены.

Email нормализуется валидатором, в частности домен приводится к нижнему регистру;
email не является средством авторизации. POST сравнивает его с email токена
(несовпадение → 403), обязательные fam/name и явно переданные phone/otc — с
сохранённым профилем (конфликт → 409 USER_PROFILE_CONFLICT). Новых пользователей
POST не создаёт и профиль не изменяет. Пропущенные phone/otc не сравниваются.

Сезон: `n/k`, `1A`, `1B`, `2A`, `2B`, `3A`, `3B` или null. Допустимы краевые
пробелы, нижний регистр, кириллические А/Б и «н/к»; ответ содержит каноническое
значение. Неизвестная категория → 422.

Время принимает `T`, часы/минуты/секунды, до 6 цифр дробной секунды и обязательный
`Z` либо числовое смещение. Например, `2026-10-31T15:00:00+03:00` возвращается как
`2026-10-31T12:00:00Z`. Naive-время и числовой Unix timestamp не принимаются.
Ограничения «только прошлое время» нет. Все ответы времени нормализованы к UTC.

## Частичное изменение

PATCH разрешён только владельцу своей `new`. Успех:
`{"state":1,"message":"Обновлено"}`. Ошибки не возвращают `state: 0` или 204.

| Вход | Результат |
| --- | --- |
| Поле пропущено | Прежнее значение сохраняется |
| `beauty_title`, `other_titles`, `connect`: null | Поле очищается |
| `level: {"spring": null}` | Очищается только весна |
| `coords: {"height": 3300}` | Меняется только высота |
| `level: {"spring": "2A"}` | Меняется только весна |
| `images: [...]` | Полная замена фото в переданном порядке |
| `images: []` | Все фото удаляются |
| `title/add_time/coords/level/images`: null | 422 |
| Компонент coords: null | 422 |
| `{}`, `coords: {}` или `level: {}` | 422 |
| `user`, `status` и неизвестные поля | 422 |

Валидный PATCH с теми же значениями может успешно вернуть 200. Ошибка в любом
поле отклоняет запрос целиком. Сохранение содержимого, координат, сезонов и фото
выполняется одной транзакцией. Сбой записи сохраняет прежние данные.

## Изображения и лимиты

`img` — обычный RFC 4648 base64 с корректным padding, без пробелов, переносов,
URL-safe-алфавита или префикса `data:image/...`. Принимаются только полностью
декодируемые однокадровые JPEG и PNG. GIF/WebP, APNG/анимация, повреждённые файлы
и произвольные байты дают 422. Декодер проверяет формат, размеры и целостность.

| Переменная окружения | По умолчанию, граница включительно |
| --- | --- |
| `FSTR_MAX_IMAGES_PER_PEREVAL` | 5 изображений |
| `FSTR_MAX_IMAGE_BYTES` | 5242880 байт одного декодированного файла |
| `FSTR_MAX_IMAGES_TOTAL_BYTES` | 20971520 байт суммы декодированных файлов |
| `FSTR_MAX_IMAGE_PIXELS` | 24000000 пикселей |
| `FSTR_MAX_IMAGE_DIMENSION` | 12000 пикселей по каждой стороне |
| `FSTR_MAX_REQUEST_BYTES` | 33554432 байта тела JSON |

Файл должен быть непустым. Для стандартного лимита одного файла base64 занимает
не более 6990508 символов. Лимиты публикуются в OpenAPI. Превышение всего тела →
413; ограничения конкретного изображения, количества или суммы файлов → 422.

Каждая запись images принадлежит одной заявке, порядок хранится в таблице связей.
Замена удаляет старые связи и принадлежащие заявке изображения внутри той же
транзакции, что сохраняет новые. GET возвращает изображения в base64; список
по email и очередь не загружают изображения/полные профили.

## Решения и история

Переходы: `new → pending → accepted` либо `new → pending → rejected`.
Обратных переходов, повторного решения и удаления заявок через API нет.

```json
{"expected_status":"new","status":"pending","reason":null}
```

Оба статуса обязательны. Для rejected нужна непустая причина 1–1000 символов.
Для других переходов reason можно опустить, передать null или допустимую строку.
Если expected_status не совпадает с текущим — 409 STATUS_CONFLICT. Если совпадает,
но переход запрещён/повторён — 409 INVALID_STATUS_TRANSITION.

Проверка и запись выполняются под `SELECT ... FOR UPDATE` той же строки, которую
блокирует PATCH содержимого. Поэтому после начала модерации PATCH получает 409,
а два решения с одним исходным статусом не могут оба пройти. Отказ не добавляет
историю. Статус и решение фиксируются/откатываются одной транзакцией.

История содержит `id`, `pereval_id`, `old_status`, `new_status`,
`actor: {user_id, role}`, `changed_at`, `reason`. История новой заявки — `[]`;
создание и PATCH содержимого в неё не входят. Изменять историю через API нельзя.

## Формат ошибок

```json
{"detail":{"code":"PEREVAL_NOT_EDITABLE","message":"Редактирование возможно только в статусе new"}}
```

Для 422 добавляется непустой массив errors:

```json
{"detail":{"code":"VALIDATION_ERROR","message":"Некорректные данные запроса","errors":[{"loc":["body","title"],"type":"string_too_short","message":"Строка слишком короткая"}]}}
```

| HTTP | detail.code |
| --- | --- |
| 401 | UNAUTHORIZED — нет действительного Bearer, также WWW-Authenticate: Bearer |
| 403 | FORBIDDEN — чужая заявка, неверная роль или подмена автора |
| 404 | PEREVAL_NOT_FOUND либо ROUTE_NOT_FOUND |
| 405 | METHOD_NOT_ALLOWED, сохраняется заголовок Allow |
| 409 | USER_PROFILE_CONFLICT, PEREVAL_NOT_EDITABLE, STATUS_CONFLICT, INVALID_STATUS_TRANSITION |
| 413 | PAYLOAD_TOO_LARGE |
| 422 | VALIDATION_ERROR |
| 500 | INTERNAL_ERROR |

В errors поля loc/type/message указывают место и тип нарушения; порядок
независимых ошибок не гарантируется. Пустой PATCH: type `empty_patch`, пустой
вложенный объект: `empty_object`, неверный JSON: `json_invalid` с loc `["body"]`.
Клиент должен опираться на HTTP, code и loc, а не на буквальный текст сообщения.

Ответы не включают исходное тело запроса, секреты, DSN, SQL и внутренние исключения.
Ошибки внешнего reverse proxy требуют отдельной настройки. Полный исполняемый
пример — [демонстрация](DEMO.md); свойства транзакций — [технические решения](DECISIONS.md).
